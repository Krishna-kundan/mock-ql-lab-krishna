## Rulings

_Format: `<ruling> — <why> — <cost if wrong>`. Stop-and-ask entries: `- ASKED: <question> — <the human's answer>`._

- Use `ql-lab` as the production stand-in for the `Production` GitHub Environment — it's the only reachable org, and it's production-type, so C7 and C12 can be proven for real — if PTSF production authenticates differently, the `Production` secret and the reviewer setup are redone at go-live, but no workflow changes.
- Swap `deploy-simple` for `deploy-multistage` as its own commit on the INT-009 branch (`a2432ae`) — the design calls it its own reviewed change, and a separate commit keeps it reviewable inside the INT-009 PR — if reviewers want it apart, it cherry-picks cleanly into its own PR.
- Production deploys use `full_build: "true"` in `prod_deploy.yml` — a manual run has no push range, so the shared action's delta would fall back to `HEAD~1` and deploy only the last commit — a full deploy takes longer and runs tests across everything in `main`; the 75% coverage risk in `ql-lab` (design §Pipeline) applies.
- `prod_deploy.yml` runs only from `main` (`if: github.ref == 'refs/heads/main'`) and one at a time (`concurrency: prod-deploy`) — a manual run can be started from any branch, and this stops a non-`main` deploy or two overlapping deploys — a run from another branch silently does nothing, which could confuse someone; the run page shows the job as skipped.
- The Code Analyzer report is written as HTML (`--output-file code-analyzer-results.html`) and uploaded as artifact `code-analyzer-<environment>`, even when the scan fails the check — the PTSF platform owner can open HTML straight from the run page — this is a local edit to the resync-managed `action.yml`, so `/ql-resync` will show it as a local diff until contributed upstream; whether the report is still written when the threshold fails is ⚠ unverified until Scene D runs.
- `config/credentials.json` records `principalType` beside `credential` and `principal` — the Connect REST call that populates a principal needs it [docs:https://developer.salesforce.com/docs/platform/named-credentials/guide/nc-populate-external-credentials.html], and a principal type isn't a secret — the design said "credential name and principal name only", so C15's key check now allows the third key; if a reviewer reads that as a design change, it goes back to `/ql-design-intent`.
- Each environment keeps all its credential values in one GitHub secret, `EXTERNAL_CREDENTIAL_SECRETS`, a JSON map keyed `<credential>/<principal>` — GitHub can't look up a secret by a name built at run time, and one map keeps every value out of the repo, reaching the script only through `env:` — one malformed secret fails every credential in that environment's run, and editing it means re-pasting the whole map.
- `credentials_reestablish.yml` offers only `CI` and `TEST`, and refuses to write unless `Organization.IsSandbox` is true — production never refreshes, and the check stops a mis-set `SFDX_URL` from overwriting production credentials — if PTSF adds a sandbox tier later, it has to be added to the dropdown.
- The workflow uses POST only on `/named-credentials/credential/`, as the docs show for populating a principal — no PUT fallback was added without reading the Connect REST reference — ⚠ unverified whether POST succeeds on a principal that already has values (for example after a refresh); if it doesn't, Scene F fails with the API's error and a PUT path is added then. The token and API version come from `sf org display --json` (field names ⚠ unverified until the first run).
- The engagement's production-stage and credential docs live in a new `.github/workflows/PRODUCTION.md`; `README.md` gets only small edits (simple pipeline marked not installed, the `main` PR check, Developer sandboxes in place of scratch orgs, the TEST typo) — `README.md` is installed from the resync template, so edits there show as a local diff on every `/ql-resync` — if the template later documents a production stage, the two overlap and `PRODUCTION.md` is trimmed.
- The `EXTERNAL_CREDENTIAL_SECRETS` example uses the `credentials` shape from the docs, an object keyed by parameter name with `{value, encrypted}` [docs:https://developer.salesforce.com/docs/platform/named-credentials/guide/nc-populate-external-credentials.html], which is what `credentials_reestablish.yml` posts unchanged — an earlier draft showed an array, which the API wouldn't accept — none if it matches; the run in Scene F confirms it.
- INT-009's go-live prerequisites (Full sandbox licence, Backup and Recover, production `SFDX_URL`, the customer's approval route, the deployment user) are checkboxes in the runbook's Go-live gate, not intent edits — they're go-live prerequisites no single criterion owns, and `golive` surfaces them — the two licences still belong in the intent's External Dependencies (known gap above).
- The post-refresh "mask sensitive data before access" runbook step is marked ⛔ and points at INT-026 and Q-design-2 — masking is INT-026's to build, and this intent must not build it — if Q-design-2 decides refreshes wait for INT-026, the step becomes "don't refresh the Full sandbox yet".
- The runbook says to delete any repo-level `SFDX_URL` and to create every GitHub Environment by hand before a workflow uses it, and the go-live gate checks both — PR #3's first `pr-validation` run (Actions run 45645227560) logged in to `ql-lab` through a repo-level `SFDX_URL` added before this build, and GitHub created the `CI` environment at the start of that run with no protection rules; by the same behaviour, a first `prod_deploy.yml` run against a missing `Production` would deploy with no reviewer (⚠ inferred from the `CI` case, not tested, because testing it means a real deploy) — if the order isn't followed, a deploy reaches an org nobody chose, or production deploys without approval, which breaks the guardrail C12 proves.
